# 개발 워크플로우

이슈를 만들고, 브랜치에서 테스트부터 짜고, PR을 열면 Claude가 리뷰한다. 머지는 사람이 한다.
사람과 Claude 세션이 같은 순서를 따른다. Claude 세션용 요약은 [CLAUDE.md](../CLAUDE.md)에 있다.

## 1. 한눈에

```
개발 계획의 단계
   │  /dev-issue  (planner)
   ▼
이슈 #n ───────────────────────────────▶ 현황판: 이슈 열림
   │  /dev-start n  (architect 설계 메모)
   ▼
브랜치 feat/n-설명 ────────────────────▶ 현황판: 진행 중
   │  test-writer: 실패하는 테스트 → 구현 → scripts/check.py
   ▼
PR #m  "Closes #n" ────────────────────▶ 현황판: 리뷰 중
   │  훅 → /dev-review m (code-reviewer)   +  GitHub Actions의 Claude 리뷰
   │  필수 지적이 있으면 고치고 다시 리뷰
   ▼
사용자가 Squash and merge → /dev-done m ─▶ 현황판: 머지, 이슈 닫힘
```

PR은 GitHub의 Pull Request다. GitLab의 MR과 같은 것이다.

## 2. 누가 무엇을 하나

| 누구 | 하는 일 |
|---|---|
| 사용자 | 방향과 범위를 정한다. 명세가 애매할 때 답한다. PR을 머지한다 |
| Claude 세션 | 이슈 발행부터 PR, 리뷰 반영, 현황판 기록까지 진행한다 |
| 에이전트 (`.claude/agents/`) | 아래 표의 일을 나눠 맡는다. 메인 세션이 부른다 |
| GitHub Actions | `ci.yml`이 PR과 main마다 확인을 돌리고, `claude-review.yml`이 PR마다 리뷰 댓글을 단다 |

| 에이전트 | 언제 | 돌려주는 것 |
|---|---|---|
| planner | 이슈를 만들기 전 | 이슈 초안: 범위, 완료 기준, 명세 근거, 테스트 계획. 크면 쪼갠다 |
| architect | 모듈이 둘 이상 걸치거나 공개 함수·API 모양이 새로 생길 때 | 설계 메모: 바꿀 파일, 함수 시그니처, 데이터 흐름, 위험 |
| test-writer | 구현 전 | 완료 기준을 덮는 실패하는 테스트. `tests/`만 고친다 |
| calc-verifier | 엔진이나 기준값을 바꾼 PR을 열기 전 | expected.json·계산 규칙과 맞는지 독립 검증한 보고 |
| code-reviewer | PR을 연 직후, 리뷰를 반영한 뒤 | 필수·권장·참고로 나눈 리뷰. PR 댓글로 그대로 올린다 |

| 스킬 (슬래시 명령) | 하는 일 |
|---|---|
| `/dev-issue <단계 또는 할 일>` | planner 초안 → GitHub 이슈 → 현황판 |
| `/dev-start <이슈>` | 최신 main에서 브랜치 → 설계 메모 → 현황판 → 실패하는 테스트 |
| `/dev-pr` | 확인 → rebase → 푸시 → PR → 현황판 → 리뷰 |
| `/dev-review <PR>` | code-reviewer → PR 댓글 → 현황판 → 반영 |
| `/dev-done <PR>` | 머지 확인 → 브랜치 정리 → 현황판 → 다음 할 일 |
| `/dev-board [sync]` | 현황판 기록 규칙. `sync`는 GitHub 상태와 현황판을 맞춘다 |

## 3. 이슈

- 코드나 문서를 바꾸는 일은 모두 이슈에서 시작한다.
- 이슈 하나는 PR 하나로 끝낸다. 바뀌는 줄이 400줄쯤을 넘을 것 같으면 쪼갠다.
- 제목: `[N단계] 할 일` (예: `[3단계] 매수일 계산과 시뮬레이션`). 단계 밖의 일은 `[버그] …`, `[문서] …`.
- 본문 칸: 단계, 배경, 할 일, 완료 기준, 명세 근거, 테스트 계획, 범위 밖. GitHub 이슈 양식과 planner가 같은 칸을 쓴다.
- 완료 기준은 테스트나 눈으로 확인할 수 있는 문장으로 쓴다. 숫자는 `expected.json`, 계산 규칙 9-8절, 시안의 값을 그대로 쓴다.

| 구분 | 값 |
|---|---|
| 종류 라벨 | `type:feat` 기능, `type:fix` 버그, `type:docs` 문서, `type:test` 테스트, `type:refactor` 구조 개선, `type:chore` 설정·도구·CI |
| 영역 라벨 | `area:engine`, `area:market`, `area:api` (main·schemas), `area:web`, `area:infra` (CI·도구·배포·워크플로우) |
| 마일스톤 | `v1` (0~8단계, F-01~F-10), `v2` (9~14단계, F-11~F-23, F-18·F-19 제외) |

## 4. 브랜치

- 최신 main에서 딴다. 이름은 `<type>/<이슈번호>-<짧은-영어-설명>`: `feat/3-buy-days`, `fix/12-fx-asof`, `chore/1-dev-setup`.
- 짧게 산다. main이 앞서가면 `git rebase origin/main`으로 따라가고 `git push --force-with-lease`로 올린다.
- main에는 직접 커밋하지 않는다.

## 5. 커밋

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/)를 따르고 설명은 한국어로 쓴다.

```
feat(engine): 월 단위 매수일 고르기

anchor 날짜가 휴장일이면 그 달의 다음 거래일을 고른다.
기간 밖의 날을 먼저 버리면 첫 달 매수일이 달라져서, 전체 거래일로 고른 뒤 자른다 (계산 규칙 2절).

Refs #3
```

- type: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`
- scope: `engine`, `market`, `api`, `web`, `docs`, `ci`, `deps`, `workflow`. 여러 곳에 걸치면 생략한다.
- 첫 줄은 50자 안쪽, 마침표 없이. 본문에는 무엇보다 왜를 쓴다.
- 커밋 하나에 논리적인 변경 하나. 커밋마다 테스트가 통과해야 한다.
- Claude가 만든 커밋은 끝에 `Co-Authored-By` 줄을 붙인다.

## 6. 테스트와 확인

순서는 빨강 → 초록 → 정리다.

1. test-writer가 완료 기준마다 실패하는 테스트를 쓴다. 실패 이유가 "아직 없음"이어야 한다. 오타나 경로 문제로 실패하면 안 된다.
2. 테스트를 통과시키는 만큼만 구현한다.
3. 중복과 이름을 정리하고 `scripts/check.py`를 돌린다.

`python scripts/check.py`가 하는 일 (CI도 같은 스크립트를 쓴다):

| 순서 | 확인 | 실패하면 |
|---|---|---|
| 1 | `ruff check .` 린트 | `scripts/check.py --fix` 뒤 남은 것을 손으로 |
| 2 | `ruff format --check .` 포맷 | `scripts/check.py --fix` |
| 3 | `mypy` 타입 (`src/`가 생긴 뒤부터, strict) | 타입을 고친다. `# type: ignore`에는 이유를 단다 |
| 4 | `pytest` | 고친다. 테스트를 지우거나 건너뛰지 않는다 |
| 5 | `node --check web/*.js` 문법, `node --test tests/web/*.test.mjs` 웹 테스트 (Node.js 22.7 이상. 로컬에 없으면 건너뛰고 CI에서는 돈다) | 고친다 |

### 끝났다고 보는 기준

- [ ] 이슈의 완료 기준을 모두 테스트하거나 눈으로 확인했다
- [ ] `scripts/check.py` 통과
- [ ] 엔진·기준값을 바꿨으면 calc-verifier 보고가 "통과"
- [ ] 화면을 바꿨으면 시안 "v1"과 비교한 스크린샷을 PR에 붙였다
- [ ] 동작이 바뀌었으면 docs/를 같이 고쳤다
- [ ] 리뷰의 필수 지적이 0개다
- [ ] 현황판에 기록했다

## 7. PR

- 제목은 squash 커밋 메시지가 되므로 커밋 첫 줄과 같은 형식으로 쓴다: `feat(engine): 매수일 계산과 시뮬레이션`.
- 본문은 템플릿(`.github/pull_request_template.md`)을 채운다. 첫 칸에 `Closes #n`을 쓰면 머지할 때 이슈가 닫힌다.
- 아직 덜 됐으면 Draft로 연다. Draft는 GitHub Actions의 Claude 리뷰가 건너뛴다.
- PR 하나는 이슈 하나. 하다가 다른 문제를 찾으면 이슈를 새로 만든다.

## 8. 리뷰

리뷰는 두 겹이다. 둘 다 `.claude/agents/code-reviewer.md`의 기준과 형식을 쓴다.

| | 세션 리뷰 | GitHub Actions 리뷰 |
|---|---|---|
| 언제 | `gh pr create`가 성공하면 훅(`.claude/hooks/after_pr_create.py`)이 세션에 `/dev-review`를 부르라고 알린다 | PR을 열거나 푸시할 때마다 (`.github/workflows/claude-review.yml`) |
| 누가 | code-reviewer 에이전트 | GitHub에서 도는 Claude Code |
| 결과 | PR 댓글 한 개, 현황판 기록 | PR 요약 댓글과 줄 단위 댓글 |
| 필요한 것 | 없음 | Claude GitHub 앱과 저장소 시크릿 `CLAUDE_CODE_OAUTH_TOKEN` (11절) |

- **필수**: 머지 전에 고친다. 버그, 명세·계산 규칙과 다름, 완료 기준에 테스트 없음, 모듈 경계 위반, 보안 문제.
- **권장**: 고치거나, 안 고치는 이유를 답글로 남긴다.
- **참고**: 질문이나 다음 이슈 거리. 할 만하면 이슈로 만든다.

필수 지적을 고친 커밋은 `fix(<scope>): 리뷰 반영 - …`로 올리고, 지적마다 어떻게 고쳤는지 답한 뒤 다시 리뷰한다. 두 번 돌아도 필수가 남으면 사용자에게 묻는다.

GitHub에서는 자기 PR을 "승인"할 수 없어서, 리뷰 결론은 댓글 첫 줄의 "머지 가능 / 고칠 것 있음"으로 남긴다.

## 9. 머지와 정리

- 머지는 사용자가 GitHub에서 **Squash and merge**로 한다. 조건: CI 통과, 필수 지적 0개, 충돌 없음.
- 머지 뒤 `/dev-done <PR>`: 로컬 main을 당기고, 브랜치를 지우고, 현황판에 머지와 이슈 닫힘을 적고, 다음 할 일을 고른다.
- 단계의 이슈가 모두 닫히면 그 단계는 완료다. [개발 계획](5_개발계획.md)의 "끝났다고 보는 기준"을 한 번 더 확인한다.

## 10. 현황판

[적립식 백테스트 개발 현황](https://claude.ai/artifact/4qzSDxqhz7o8zoeF2CvucF)에 단계·이슈·PR·리뷰를 서로 이어서 남긴다. 원본은 GitHub이고, 현황판은 그것을 한눈에 보는 기록이다. 비공개라서 다른 사람에게 보여 주려면 페이지의 Share에서 공유한다.

| 일이 생기면 | 현황판에 |
|---|---|
| 이슈를 만듦 | 이슈 줄 추가, 단계와 연결, 작업 기록 한 줄 |
| 브랜치를 땀 | 이슈 "진행 중"과 브랜치 이름, 단계 "진행 중" |
| PR을 엶 | PR 줄 추가(이슈와 연결), 이슈와 단계 "리뷰 중" |
| 리뷰가 끝남 | PR의 리뷰 결론, 지적 수, 리뷰 댓글 링크 |
| 머지함 | PR "머지됨", 이슈 "닫힘", 단계의 이슈가 다 닫혔으면 단계 "완료" |

기록하는 법(문서 구조와 필드)은 `.claude/skills/dev-board/SKILL.md`에 있다.

### 결정 보드

사용자가 자리를 비운 동안 Claude가 혼자 정한 것과 사용자가 직접 해야 할 일은 [결정 보드](https://claude.ai/artifact/JaxQyqXbXZLdmN4houmWh5)에 모은다 (컬렉션 `data/dev/decisions`). 항목마다 물어볼 것, 고른 것, 이유, 다른 선택지, 되돌리는 법을 적는다. 사용자가 보드에서 "좋아요"나 "바꿔 주세요"를 누르면 답이 `data/dev/answers`에 남고, 다음 세션에서 Claude가 그 답을 읽어 반영한 뒤 항목의 `status`를 `done`으로 바꾼다.

## 11. 처음 한 번 할 일

### GitHub에서 Claude 자동 리뷰 켜기

`claude-review.yml`은 시크릿이 없으면 리뷰를 건너뛰고 초록으로 끝난다. 켜려면:

1. Claude GitHub 앱을 이 저장소에 설치한다: https://github.com/apps/claude
2. 터미널에서 `claude setup-token`을 실행해 토큰을 받는다. 브라우저로 로그인하면 1년짜리 토큰을 한 번 보여 준다 (Pro·Max 이상 구독).
3. 저장소 Settings → Secrets and variables → Actions → New repository secret에서 이름 `CLAUDE_CODE_OAUTH_TOKEN`으로 넣는다.

터미널 Claude Code의 `/install-github-app`도 1~3을 안내한다. 그 명령이 워크플로우 파일을 더하는 PR을 따로 열면, 이 저장소에는 이미 `claude-review.yml`이 있으니 그 PR은 닫는다.
Team·Enterprise 플랜이면 워크플로우 없이 Anthropic이 운영하는 Code Review를 켜는 방법도 있다.

### 저장소 설정 (권장)

- Settings → General → Pull Requests: "Allow squash merging"만 남기고, "Automatically delete head branches"를 켠다.
- Settings → Branches: `main` 보호 규칙. PR을 거쳐야 머지, CI 통과 필수, force push 금지.

`.claude/settings.json`의 deny 규칙은 main으로 push하거나 force push하는 흔한 명령 모양만 막는다. 규칙은 명령 글자를 맞춰 볼 뿐이라 main에서 인자 없이 `git push`하는 것 같은 경우는 못 막는다. 실제 방어는 위의 `main` 보호 규칙이다.
